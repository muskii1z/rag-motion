### Teach-back 1: after Step 4 (2026-09-24)

**The developer's explanation** (lightly condensed, their wording kept):
"So far we installed uv, it's a Python library, I think. Then we made the GitHub. Then we created our database, inside a Docker container. Then we created the database table structure. It's PostgreSQL, and it has a pgvector extension. PostgreSQL is just regular, you can store text, like type of exercise, equipment, what muscle, etc. The vector extension and vector storage basically allows us to identify those specific parts of the table, or any item, with a number, labels it with a number, and the idea is that if I have three leg exercises, those numbers would be closer than an arm and a leg exercise."

**What was right.** The overall picture.
- GitHub. Plus: `.gitignore` keeps API keys off GitHub ([.gitignore](concepts.md#gitignore)).
- Database in a Docker container. Plus: the volume is where the data actually lives, so containers can be rebuilt ([Docker volume](concepts.md#docker-volume)).
- PostgreSQL is the database and `exercise` is the table in it, with regular columns for equipment, muscles, and difficulty ([Schema](concepts.md#schema)).
- The leg-vs-arm intuition is exactly right: similar exercises sit closer together.

**What was corrected.**
1. **uv is not a library, it's a tool.** Libraries are code the project uses (anthropic, voyageai). uv installs them into the project's private folder and records exact versions. uv is the delivery driver; libraries are the packages. See [Package manager](concepts.md#package-manager).
2. **The vector isn't a label or a single number; it's a list of 1,024 numbers.** The labels are the `id` and `slug` (e.g. `goblet-squat`). The vector describes the exercise's meaning, not its name. Think of coordinates: a map location needs 2 numbers, meaning needs about 1,024. Similar meanings sit near each other, and `<=>` measures the distance. See [Embedding](concepts.md#embedding).
- Also clarified: the `embedding` column is currently empty. Postgres doesn't create vectors. Voyage reads each description and returns the 1,024 numbers (Step 8); pgvector stores them and measures distance. See [pgvector](concepts.md#pgvector).

**Interview version** (saved verbatim at the developer's request):

> I used uv to set up the Python project and its dependencies, and pushed it to a private GitHub repo with secrets git-ignored. I run PostgreSQL in Docker, with a volume so the data persists. I created an exercise table with regular columns for things like equipment and difficulty, plus a vector column from the pgvector extension. Each exercise's description gets turned into a 1,024-number embedding, so exercises with similar meanings sit close together, and I can search by meaning and filter by the regular columns in the same query.

Note: the last sentence describes the design. Embeddings are created in Step 8 and search is built in Step 9; neither exists yet. (As of Step 5 the table holds 20 seeded exercises, all with empty embeddings.)

### Teach-back 2: evaluation, during the eval walkthrough (2026-09-25 to 2026-09-28)

**The developer's explanation** (their words):
"A bunch of test questions to see how accurate or inaccurate we are; the first time you run it, it's a baseline; if we change anything, the way it responds to the same baseline questions determines whether we got worse, better, or stayed the same."

**What was right.** The core idea: a fixed set of questions, a first run as the baseline, and later runs compared against it. See [Baseline and benchmark](concepts.md#baseline-and-benchmark).

**What was refined.**
1. **Keep the questions fixed to compare.** Changing the questions or the key changes the ruler, which creates a new version and a new baseline. During the review, scores moved with no system change at all. See [When the answer key changes, the scores change](concepts.md#when-the-answer-key-changes-the-scores-change).
2. **The answer key must be right, or the scores are meaningless.** The same search scored recall 0.80 or 1.00 on one question depending on the key. See [Answer key](concepts.md#answer-key-an-eval-as-a-practical-exam).
3. **Look at individual questions, not just totals.** The averages hide which questions fail and why.
4. **Small differences are noise.** With 31 questions, one question is about 3%. See [Small-sample noise](concepts.md#small-sample-noise).
- Also clarified: `reviewed: false` is a label (the coach hasn't checked that key yet) and doesn't change grading. `expected_coverage` is a field on every question; `coverage-gap` is a category of 2 deliberately unanswerable questions.
- The developer's later insight, during the review: "when we bring in new material, that's where evals are useful, because we can test against the same standard of questions." Refinement: if the new material changes what's correct, update those keys deliberately; that version becomes the new baseline.

**Suggested interview version** (drafted by the scribe from the points above; not yet approved by the developer):

> My eval is a fixed set of 31 test questions with an answer key. The first run is the baseline; after any change I re-run the same questions and compare, question by question, to see whether we got better, worse, or stayed the same. The key has to be right, so I reviewed every expected answer myself as a coach. And I only compare runs graded with the same version of the key, because changing the key moves the scores even when the system hasn't changed.

## Phase 1 in one paragraph

**DRAFT by the scribe, for the developer to adapt into their own words. Not yet approved.** Every fact is from the [build log](build-log.md) and the [README](../README.md); the phrasing is a suggestion.

> In Phase 1 I built a retrieval-augmented assistant for coaches. It searches 20 exercises I wrote and about 200 passages from openly licensed sources (the U.S. Physical Activity Guidelines, my own notes drafted from NSCA position statements, and two CC BY research papers), stored in Postgres with pgvector. A question is embedded, the top five exercises and top five passages go to an LLM through OpenRouter with a strict output schema, and Python checks every citation against what was actually retrieved. Every request is traced in LangSmith. To know whether it works, I wrote a 31-question eval and reviewed every answer key myself as a coach. On that eval it finds the right exercises about 9 times in 10 and the right passages 97 times in 100, every citation pointed to retrieved evidence, and it was honest about gaps on 29 of 31. Its weakness is respecting a person's limits: it suggested bench exercises to someone with only dumbbells, and older-adult advice to a beginner. That's a filtering problem, not a search problem, so the next phase strengthens the eval first, then adds metadata filters and measures them against the same baseline. Before touching search code, I added 31 fast tests, including the real citation bugs I hit, plain error messages, and a README that lets a fresh clone rebuild the whole system.

Numbers behind it: [reviewed baseline](build-log.md#lesson-3-the-reviewed-baseline) (semantic exercise recall 0.91, passage recall 0.97; answers: citations 31/31, coverage 29/31, expected evidence 30/30, forbidden 2/5); [Step 16](build-log.md#step-16-tests-error-handling-readme-phase-1-complete) (31 tests, about 0.3 s); [0023](decisions/0023-phase-1-completion-tests-and-errors-before-retrieval-changes.md) (why tests before filters).

## Phase 1F (filters) in one paragraph

**DRAFT by the scribe, for the developer to adapt into their own words. Not yet approved.** Every fact is from the build log entries F1 to F6; the phrasing is a suggestion.

> After Phase 1, my eval showed one clear weakness: answers broke the person's limits, like bench exercises for someone with only dumbbells, or older-adult numbers for a beginner. I fixed it in a set order. First I doubled the exercise catalog to 42, then rebuilt the eval for it, with 13 questions that test limits, one trap question with no limits, and an AI judge for my coach's labeling rules. Only then did I build the fix: a small LLM call reads the equipment and age group from the question, and the database search filters on them, so the model never sees what the person can't use. Each filter went in on its own and was measured on the same test. Single runs turned out to be noisy, so the final comparison is three runs per version on the same answer key: without filters, 4 of 13 limit questions broke a limit on every run; with filters, none did, and citations, evidence use, and coverage stayed the same.

Numbers behind it: [F6](build-log.md#phase-1f-f6-re-run-the-eval-compare-before-and-after-the-filters-update-the-readme) (69% → 100% no forbidden advice; citations 98% both; expected evidence 98% both; coverage 88% → 91%); [F3 + F4](build-log.md#phase-1f-f3--f4-read-equipment-limits-from-the-question-and-filter-exercises) and [F5](build-log.md#phase-1f-f5-population-tags-on-passages-and-a-population-filter) (each filter measured separately); [0028](decisions/0028-before-after-averaged-over-three-runs.md) (why 3 runs).

## Final results in one paragraph (going public)

**DRAFT by the scribe, for the developer to adapt into their own words. Not yet approved.** Every fact is from the [going-public build-log entry](build-log.md#finishing-phase-1f-for-a-public-portfolio-coach-reviews-final-evals-readme-rewrite-pre-public-checks) and the [README](../README.md).

### How did you structure your LLM outputs?
Evidence so far:
- *(Superseded by Step 6, below.)* Original plan: `client.messages.parse` with a Pydantic model (a Python class defining the exact output shape). See [0003. LLM: Claude Opus 5](decisions/0003-llm-claude-opus-5.md).
- First structured Claude call is planned for Step 6 (prose to structured client profile).
- [Step 1](build-log.md#step-1-install-uv-create-the-python-project-add-dependencies): pydantic 2.13.5 and the anthropic SDK 1.8.0 are installed and import cleanly. See [What each library is for](concepts.md#what-each-library-is-for).
- [Step 5](build-log.md#step-5-write-20-exercises-seed-script-query-by-hand): the provider is now open. The developer prefers [OpenRouter](concepts.md#openrouter) (one key, many models), so 0003 is "under review" until Step 6. Point to make: structured-output support varies by model on OpenRouter, so the model choice has to be checked against the output shape we need. The `client.messages.parse` plan may not apply.
- [Step 5](build-log.md#step-5-write-20-exercises-seed-script-query-by-hand): the same technique already works on input data. The `Exercise` [Pydantic model](concepts.md#pydantic-model-and-literal-types) with `Literal` types validates every seed entry and names the failing field. A structured LLM output would be checked against a model like this.
- [Between Steps 5 and 6](build-log.md#a-api-keys-and-openrouter-setup): with OpenRouter, one key works with every model and the model is a string chosen per request, so it can be swapped or compared in one line. Structured-output support is one of the three criteria (with price and speed) for picking the Step 6 model, because Step 6 depends on it. See [OpenRouter](concepts.md#openrouter) (extended).
- **[Step 6](build-log.md#step-6-first-llm-call-via-openrouter-prose-to-structured-client-profile): built and tested. The strongest evidence so far.** Commit `72360f9`.
  - **Strict schema from Pydantic.** `ClientProfile` (goal, sessions per week, session minutes, equipment, unmapped equipment, experience level, age, context notes) is turned by the `openai` SDK into a strict JSON schema: every field required but nullable, no extra fields, equipment limited to the same 7 names as the exercise table, experience level a fixed list or null. `chat.completions.parse()` validates the reply back into the object. See [Structured output (strict JSON schema)](concepts.md#structured-output-strict-json-schema) and [LLM as a software component](concepts.md#llm-as-a-software-component).
  - **Shape vs content, the key lesson.** In the first version every output passed validation, yet: a TRX strap became `band`, "early 30s" became age 30, notes filled with the model's own advice, and an injected instruction flipped an "advanced lifter" to beginner. Point to make: structured output guarantees the shape, not the truth. See [Hallucinated inference](concepts.md#hallucinated-inference).
  - **Fixes by prompt rules:** numbers only from the text; hedges become null with the exact wording in notes; true equipment equivalents only; notes are facts only.
  - **Deterministic missing fields.** The LLM invented names when asked what was missing, so Python's `missing_fields()` now computes it from nulls. Point to make: don't ask the LLM for what code can compute exactly. See [Deterministic vs generated](concepts.md#deterministic-vs-generated).
  - **Guards around the call:** `max_tokens=1000` (a missing cap once broke a request), `temperature=0`, and checks for a cut-off reply, a refusal, or a parse failure. See [Output length cap (max_tokens)](concepts.md#output-length-cap-max_tokens) and [Temperature](concepts.md#temperature).
  - Provider and library: OpenRouter with the `openai` SDK, default Qwen3 235B, model switchable with `LLM_MODEL`. See [0013](decisions/0013-llm-openrouter-openai-sdk-qwen.md) and [OpenAI-compatible APIs](concepts.md#openai-compatible-apis).
- [Step 10](build-log.md#step-10-rag-grounded-cited-answers-plus-a-minimal-local-web-ui): a second structured output, and one shared wrapper for both.
  - `GroundedAnswer`: `answer` (prose with inline `[slug]` citations), `cited_slugs`, `evidence_coverage` (`full` / `partial` / `none`), `gaps`. Structured so code can check the citations and the page can show a coverage badge. See [Grounding (grounded answers)](concepts.md#grounding-grounded-answers).
  - `structured_completion()` in `llm.py` works with any Pydantic model and holds every guard once (`max_tokens`, `require_parameters`, usage accounting, truncation/refusal/parse checks). See [One module per provider](concepts.md#one-module-per-provider) (extended).
  - A new failure of structured output: the model pasted its own field names ("evidence_coverage: partial") into the answer text. Fixed with a prompt rule.
  - Default model is now `google/gemini-2.5-flash-lite` ([0013 update](decisions/0013-llm-openrouter-openai-sdk-qwen.md#update-2026-09-25-step-10-default-switched-to-gemini-25-flash-lite)).
- [Step 15](build-log.md#step-15-evaluation-baseline-for-retrieval-and-answers): **structured output made the answers scorable by code.** Because `evidence_coverage` and `cited_ids` are separate typed fields, the answer eval compares them directly with expected values: the coverage label matched 25 of 29 expected labels, and citations were checked for validity, expected evidence, and forbidden items without any LLM judge. See [Code-based evaluators vs LLM-as-judge](concepts.md#code-based-evaluators-vs-llm-as-judge).
  - Point to make: "I structured the answer so it could be tested. A free-text answer would have needed another model to grade it."
- [Phase 1F, F2](build-log.md#phase-1f-f2-strengthen-the-eval-and-record-the-before-baseline): **structured output for a judge, too.** The AI judge returns a typed result: for each rule a verdict limited to `pass` / `fail` / `not_applicable` plus a one-sentence reason. That lets its verdicts become LangSmith scores and be printed for the coach to check. It reuses `structured_completion()` with a different model (`anthropic/claude-sonnet-5.5`), `temperature=0`, and `max_tokens=1500`. See [LLM-as-judge (AI judge)](concepts.md#llm-as-judge-ai-judge).
  - Point to make: "Where I did need a model to grade answers, I made the grader return structured verdicts with reasons, so its output is as checkable as the answer's."
- [Phase 1F, F3 + F4](build-log.md#phase-1f-f3--f4-read-equipment-limits-from-the-question-and-filter-exercises): **structured output that feeds a filter.** `extract_limits` fills a `QuestionLimits` form (`equipment_limited`, `equipment_owned` in the catalog's allowed names, and `limit_phrase`, the exact words that state the limit) at `temperature=0`, `max_tokens=300`. The typed output goes straight into the SQL filter. Code, not the model, adds `bodyweight`. Correct on all 40 eval questions, $0.0013 for all of them. See [Query understanding](concepts.md#query-understanding-reading-limits-from-the-question), [Structured output](concepts.md#structured-output-strict-json-schema) (extended), [Deterministic vs generated](concepts.md#deterministic-vs-generated) (extended).
  - Point to make: "The model only reads the language: what equipment does this person say they have. It returns names from my own equipment list, and Python applies the rules, like 'everyone can do bodyweight'."
- [Phase 1F, F5](build-log.md#phase-1f-f5-population-tags-on-passages-and-a-population-filter): **the form gained a field, and the prompt needed a fix.** `QuestionLimits` now has `population` (a `Literal` of adults, older-adults, youth, pregnancy, or null), filled by the same call. The model first read "athletes" and "an intermediate lifter" as adults on 4 questions, despite the prompt. Spelling out which words do *not* name a group fixed all 40. See [Saying what not to infer](concepts.md#saying-what-not-to-infer-default-assumptions-in-extraction-prompts), [Query understanding](concepts.md#query-understanding-reading-limits-from-the-question) (extended).
  - Point to make: "Structured output makes the model's reading checkable. I could see it defaulting 'athlete' to 'adult' on four questions, fix the prompt, and confirm all 40 were right before any filter used it."
- [Phase 1F, F7b](build-log.md#phase-1f-f7b-experiment-with-the-coachs-presentation-rules-in-the-answer-prompt-reverted): **format rules in the prompt, measured and reverted.** Asking the small answer model (`google/gemini-2.5-flash-lite`) to group and label its prose made focused answers padded and coverage claims less accurate; none of three versions beat the plain prompt ([0030](decisions/0030-answer-prompt-stays-without-presentation-rules.md), proposed). The labels are catalog facts, so the idea for later is to show them in code, next to each citation, rather than in the model's text. See [Prompt rules have a ceiling](concepts.md#prompt-rules-have-a-ceiling-especially-on-small-models) and [Deterministic vs generated](concepts.md#deterministic-vs-generated).
  - Point to make: "Structure I can check, like typed fields and citation ids, works well. Formatting I asked for in prose, like labels and headings, was followed unreliably by a cheap model and changed other behavior. Facts the database already has belong in code, not in the prompt."

- [Going public, 2026-10-01](build-log.md#finishing-phase-1f-for-a-public-portfolio-coach-reviews-final-evals-readme-rewrite-pre-public-checks): **a structured reading that over-reached.** One prompt line taught `extract_limits` that a request for bodyweight exercises means no equipment. Because its output is a typed form, a check over all 52 questions showed exactly which ones flipped: "KBS for hip power" and a band-pulling question became limited too. A second line fixed it; the check, run twice, showed 8 limited questions, as intended. See [0042](decisions/0042-bodyweight-requests-are-a-no-equipment-limit.md).
  - Point to make: "Structured output let me diff the model's reading across every question before and after a prompt change. That's how I saw my fix break two questions it wasn't meant for."
- [Phase 2, step 1](build-log.md#phase-2-step-1-the-program-agent-loop-conversation-and-tools): **a structured output as a tool.** The program agent returns its program by calling `submit_program`, whose input schema is built from the `ProgramDraft` Pydantic model (days, exercises with sets, reps, rest; progression; rationale; cited ids; safety notes). Nested definitions are written out in place (`_inline_refs`), a test checks for leftover `$ref`, and a program that fails validation goes back to the agent as the tool result. See [Structured output](concepts.md#structured-output-strict-json-schema) (extended) and [Tool calling](concepts.md#tool-calling-function-calling).

- [Phase 2, step 2](build-log.md#phase-2-step-2-program-checker-in-code-agent-guardrails-and-the-agent-model-choice): **structured checks, not just structured outputs.** Each program check returns a `Check` (name, passed, detail, fix). The failed ones go back to the agent as data, with `exactly_what_to_change` listing each fix. The same structure prints as "Program checks: X/Y passed" in the terminal.
  - Point to make: "I structure my code's feedback to the model the same way I structure the model's output to me: typed fields, so nothing has to be parsed out of prose."

- [Phase 2, step 2 fixes](build-log.md#phase-2-step-2-fixes-health-issues-read-by-the-profile-ai-and-no-guessed-bodyweight): **a new field instead of a word list, and a reader that guessed.** `ClientProfile` gained `health_issues` (injuries, pain, conditions, surgeries, pregnancy, in the client's words, never a diagnosis), because a word list missed "tweaked my back". The same reader guessed equipment `['bodyweight']` for "beginner to the gym" in 1 of 3 reads at temperature 0. The prompt now says never to default to bodyweight, and code resets that guess unless the client said it ([0055](decisions/0055-bodyweight-only-when-the-client-says-so.md)).
  - Point to make: "Structured output gives me fields I can check in code, so when the reader guessed a value, I could write a rule against that exact guess. A typed field is only trustworthy if something checks how it got filled."

## RAG

### Why did you use RAG instead of simply prompting the model?
Evidence so far:
- [LLM vs embedding model](concepts.md#llm-vs-embedding-model): the database finds relevant exercises before Claude ever sees the question.
- [0002. Embeddings with Voyage AI](decisions/0002-embeddings-voyage-4-lite.md)
- [Why RAG beats a plain chatbot here](concepts.md#why-rag-beats-a-plain-chatbot-here) (discussed before [Step 4](build-log.md#before-we-started-how-much-does-the-table-lock-us-in)): the honest four-point answer. A general chatbot already knows training principles and would write a decent program, so the advantage is not that the model knows more. It is: (1) every claim has a source a coach can check; (2) it only uses catalog exercises that fit the client's equipment and level; (3) the knowledge is controlled and vetted by the developer, not whatever the model absorbed from the internet; (4) it is measurable through evaluation.
- Supporting pieces already built in [Step 4](build-log.md#step-4-exercise-schema-create-the-table-inspect-it-in-psql): the required `source` column (point 1), the constrained `equipment` and `difficulty` columns (point 2), and the unique `slug` used for citations and eval tests (points 1 and 4).
- [Structured vs unstructured knowledge](concepts.md#structured-vs-unstructured-knowledge): a strong answer needs both an exercise catalog (rows) and training principles (document text). Only the catalog exists so far.
- [Content licensing in RAG](concepts.md#content-licensing-in-rag): part of point 3. The knowledge must be content we have permission to use, so copyrighted textbooks can't go in the public repo. Source choice is still open.
- [Step 5](build-log.md#step-5-write-20-exercises-seed-script-query-by-hand): [RAG: Retrieve, Augment, Generate](concepts.md#rag-retrieve-augment-generate). A clear breakdown to say out loud: retrieve evidence from your own data, augment the prompt with it, generate a cited answer. Seeding and a single LLM call are pieces of RAG, not RAG. Step 5 gives R something to search; Step 6 is G alone; Steps 7 to 9 are R alone; Step 10 connects them.
- [Step 5](build-log.md#before-we-started-four-questions-and-a-plan-change): why a structured catalog **and** documents. Documents answer "why and how to train"; the catalog answers "what exists". An agent that builds programs needs filterable rows ("3 lower-body power exercises that only need a box"), which can't be pulled reliably from paragraphs. See [Structured vs unstructured knowledge](concepts.md#structured-vs-unstructured-knowledge) (extended).
- [Step 5](build-log.md#step-5-write-20-exercises-seed-script-query-by-hand): why clean data first. [Seeding](concepts.md#seeding) is the simplest ingestion; document ingestion (Steps 12 to 14 then; Steps 11 to 13 since the reorder after Step 10) adds failure points (garbled PDF text, chunks cut mid-sentence, wrong chunk sizes, lost metadata). Building it first would make failures impossible to locate. Good story: the developer challenged the order, and the plan was revised ([0011](decisions/0011-phase-1-plan-revision-ingestion-and-langsmith.md)).
- [Step 5](build-log.md#step-5-write-20-exercises-seed-script-query-by-hand): provenance is honest. Every exercise's `source` is "Drafted with AI assistance; pending coach review" until the developer reviews it.
- Full answer still needs Step 10 (retrieved evidence to the LLM, cited answer), Steps 12 to 14 (documents; now Steps 11 to 13), and Step 15 (eval baseline). *Step 10 is now done (below).*
- [Step 6](build-log.md#step-6-first-llm-call-via-openrouter-prose-to-structured-client-profile): the G (generation) half now works on its own: a validated LLM call with a typed output. It also showed why generation alone isn't enough: without evidence to check against, the model filled gaps with plausible guesses ([Hallucinated inference](concepts.md#hallucinated-inference)). Still not RAG; retrieval (Steps 7 to 9) and connecting them (Step 10) come next.
- [Step 7](build-log.md#step-7-first-embedding-embed-one-sentence-look-at-the-numbers): the first piece of R (retrieve). Text and questions become vectors, and similarity ranks them. Nothing is stored or searched in the database yet (Steps 8 and 9).
- [Step 8](build-log.md#step-8-embed-all-exercises-store-vectors-compare-them-by-hand): the stored half of R. All 20 exercises now have vectors in pgvector, and hand-run nearest-neighbor queries showed they group sensibly. Searching them with a question is Step 9; connecting search to the LLM is Step 10.
- [Step 9](build-log.md#step-9-similarity-search-from-the-command-line-judge-results-by-eye): R works end to end on the real catalog (question → top 5 exercises).
- **[Step 10](build-log.md#step-10-rag-grounded-cited-answers-plus-a-minimal-local-web-ui): RAG built. The strongest evidence so far.** Commit `4b58cb2`. See [RAG: Retrieve, Augment, Generate](concepts.md#rag-retrieve-augment-generate) (extended with the real diagram) and [Why RAG beats a plain chatbot here](concepts.md#why-rag-beats-a-plain-chatbot-here) (extended).
  - **Admitting a gap instead of inventing.** The catalog has no curls. Asked "what exercises can i do for biceps", the grounded answer (Qwen) used only the two rows that list biceps, marked the other three retrieved exercises "not used", and said coverage was partial: no isolation exercises such as curls. A plain chatbot would just suggest curls. See [Grounding (grounded answers)](concepts.md#grounding-grounded-answers).

### How did you handle PDF extraction? (interview material)
Not a question from the brief, but a common one for RAG roles: ingestion quality decides retrieval quality.
Evidence so far:
- [Step 11](build-log.md#step-11-document-ingestion-extract-clean-page-text-from-the-physical-activity-guidelines-pdf): the full story, in order, in [the investigation](build-log.md#the-investigation-from-raw-text-to-clean-pages).
  - **Why it's its own step.** A PDF stores positioned characters, not paragraphs, so extraction rebuilds reading order. Errors fail silently and poison chunks, embeddings, and retrieval. See [PDF text extraction and reading order](concepts.md#pdf-text-extraction-and-reading-order) and [Garbage in, garbage out](concepts.md#garbage-in-garbage-out-ingestion-quality).
  - **Measure first.** Raw pass: 118 pages, 40,775 words, 10 nearly empty pages (the chapter title pages), 60 line-end hyphens.
  - **The hidden running header.** Exact matching missed it because each copy had its own page number; normalizing digits found it on 54 pages. See [Running headers and footers](concepts.md#running-headers-and-footers-normalize-before-comparing).
  - **Hyphens.** "moderate-to-vigorous" breaks across lines at a real hyphen; deleting line-end hyphens would mangle it. Rule: join and keep the hyphen. See [Line-end hyphens](concepts.md#line-end-hyphens-hyphenation-ambiguity).
  - **Layout, not text patterns.** Footers dropped by position (y ≈ 747–761 on a 792-pt page); paragraphs rebuilt from line gaps (~3 pt vs ~12 pt); headings found by font size (body 10 pt, headings 12 pt+; 264 detected); bullets kept on their own lines. See [Position-based cleaning](concepts.md#position-based-cleaning-coordinates) and [Font size as structure](concepts.md#font-size-as-structure-heading-detection).
  - **Checked, not assumed.** 488 fewer words after cleaning, explained by the removed footers; the running header went from 54 pages to 0. See [Sanity-checking a transformation](concepts.md#sanity-checking-a-transformation-account-for-what-was-removed).
  - **Library choice.** PyMuPDF over pypdf and pdfplumber, for positions and font sizes. See [0018](decisions/0018-pdf-extraction-pymupdf-layout-cleaning.md).
- Limits worth saying: thresholds are tuned to this one PDF; numeric grid tables not examined yet; the PDF's tags aren't used.
- [After Step 15](build-log.md#after-step-15-trace-cleanup-two-research-papers-eval-set-v2): **the best extraction is sometimes no PDF extraction.** The two research papers (Kons 2023, Haugen 2019) were two-column PDFs, which would have needed new layout rules. Europe PMC had them as JATS XML, a standard format that labels sections, paragraphs, lists, and tables, so the chunker reads the tags instead. Tables come out row by row; in-text markers like `[12]` are stripped so the model can't copy them into answers and trip the citation checker. Cost: a second reader and no page numbers for these passages. See [Structured XML (JATS) vs PDF](concepts.md#structured-xml-jats-vs-pdf-for-research-papers), [Stripping bibliography markers](concepts.md#stripping-bibliography-markers-to-protect-citation-checks), and [0022](decisions/0022-research-papers-europe-pmc-jats-xml-not-pdfs.md).
  - Point to make: "Same lesson twice: prefer a structured source when one exists. For papers, that meant the archive's XML instead of the two-column PDF."

**Teach-back-ready:**
> I treated extraction as its own step, because PDFs store positioned characters, not paragraphs, and bad extraction silently ruins everything downstream. I used PyMuPDF, which gives me each line's position and font size. First I measured the raw output. My repeated-line check missed the running footer because every copy had a different page number, so I normalized digits and found it on 54 pages. Then I cleaned by layout: dropped footers by their position, rebuilt paragraphs from the gaps between lines, marked headings by font size, and kept hyphens in compounds like "moderate-to-vigorous". To check I hadn't lost content, I accounted for the word difference: 488 words, which the removed footers explain. I keep the raw text next to the cleaned text for debugging, and the thresholds are documented constants, because they're tuned to this document and may need retuning for the next one.

### How did you chunk your documents? (interview material)
Not a question from the brief, but nearly every RAG interview asks it. Chunking means splitting documents into passages that are embedded and retrieved one at a time.
Evidence so far:
- [Step 12](build-log.md#step-12-chunking-split-sources-into-passages-and-store-them-in-a-second-table-with-metadata), with the full design in [0019](decisions/0019-structure-aware-chunking-150-450-labels-no-overlap.md).
  - **Options weighed.** Fixed size with overlap (the industry default, about 500–1,000 tokens with 10–20% overlap), section by section, structure-aware with size limits, and semantic. See [Chunking approaches](concepts.md#chunking-approaches-fixed-size-section-structure-aware-semantic).
  - **Why size matters.** Too small loses context; too large blurs the embedding and fills the prompt. See [Chunk size](concepts.md#chunk-size-too-small-vs-too-large).
  - **Measured first.** The Guidelines' 256 sections: median 116 words, 54 under 50 (infographic scraps like "YOUR WAY"), 2 over 600 (a 1,341-word glossary). That ruled out pure section chunks (too many fragments) and pure fixed size (blends topics). See [Measure the corpus before choosing parameters](concepts.md#measure-the-corpus-before-choosing-parameters).
  - **The method.** Split at headings, never across chapters, merge small sections to about 150 words, split big ones at paragraph breaks below about 450, never mid-sentence, drop scraps under 4 words, skip noise pages listed in the manifest. See [Structure-aware chunking with size limits](concepts.md#structure-aware-chunking-with-size-limits).
  - **No overlap; labels instead.** Each chunk is embedded with "title > chapter > sections" in front of it. See [Contextual labels instead of overlap](concepts.md#contextual-labels-instead-of-overlap).
  - **Result.** Guidelines: 133 chunks, 83 / 253 / 519 words (min / median / max). Notes: 14 chunks. 10 of 133 fall outside the band, each explained.
  - **Inspected by hand.** Chunk #57 is exactly the key adult guidelines (Chapter 4, page 56). The smallest (#33) is only a figure caption, because charts don't survive text extraction ([Figures and charts lost in extraction](concepts.md#figures-and-charts-lost-in-extraction)).
  - **Bugs found and fixed.** The first merge logic lost page numbers (rewritten to keep paragraphs with their pages until the end); note labels repeated the title (fixed in `embed_text_for()`).
  - **Built to be compared.** Every row records its chunker and settings, so Step 15 can test fixed-size against this on the same questions. See [Chunker version on every row](concepts.md#chunker-version-on-every-row).
- Limits worth saying: the rules suit heading-rich documents and depend on Step 11's heading detection (a page 108 heading-order issue may misfile a few Appendix 1 subsections); the 150/450 numbers are untested guesses until Step 15.

**Teach-back-ready:**
> I compared four ways to chunk: fixed-size windows with overlap, which is the common default; one chunk per section; structure-aware with size limits; and semantic splitting. Before choosing, I measured the document: its 256 sections had a median of 116 words, 54 were under 50 words, and two were over 600. So one-chunk-per-section would give me dozens of useless scraps, and fixed windows would cut mid-sentence and mix topics. I went structure-aware: split at headings, never cross a chapter, merge small sections up to about 150 words, split big ones at paragraph breaks below about 450. Instead of overlap, each chunk is embedded with a label like "Guidelines > Chapter 4. Active Adults > Key Guidelines for Adults", so even a short passage knows what it's about. Every chunk stores its source, pages, and license, so answers can cite a page, and it stores the chunker settings, so I can put a fixed-size version next to it and let my evaluation decide which retrieves better.
- [Step 15](build-log.md#step-15-evaluation-baseline-for-retrieval-and-answers): **the eval is ready to compare chunkers, but the comparison hasn't been run.** Expected passages are written as matchers (source + pages, heading, or chapter), not chunk ids, so the same eval works on any chunker. See [Eval matchers that survive re-chunking](concepts.md#eval-matchers-that-survive-re-chunking). The baseline used `structure-v1(min=150,max=450)` only; the fixed-size comparison is still to do.
- [After Step 15](build-log.md#after-step-15-trace-cleanup-two-research-papers-eval-set-v2): **tables broke the size rule.** One table became a 1,265-word chunk because the splitter looks for sentence ends and a table has none. Oversized tables and lists now split by rows, with the caption repeated on each piece. After: Kons 25 chunks (median 343, max 448 words), Haugen 28 (median 365, max 508); the Guidelines' 133 chunks unchanged. See [Splitting tables by rows with repeated captions](concepts.md#splitting-tables-by-rows-with-repeated-captions).
- [Phase 1F, F5](build-log.md#phase-1f-f5-population-tags-on-passages-and-a-population-filter): **storing structure on every chunk paid off later.** Because each chunk kept its chapter and headings (Step 12), population tags were derived from them by rules and back-filled without re-chunking or re-embedding. See [Tagging passages from document structure](concepts.md#tagging-passages-from-document-structure-rules-not-an-llm).

### Critiquing RAG advice (interview material)
Not a question from the brief, but a strong story: being able to judge popular advice with specifics. Between Steps 5 and 6 the developer brought in the article "RAG Is Simpler Than You Think" (Rafael Pierre, Lighthouse newsletter, June 2026). The review kept what was right (start simple and measure, cheap query rewriting, jargon breaks general embeddings, split multi-intent questions) and named what was weak: a keyword-first "hybrid" that can't recover synonyms, overstated pain of pre-computed embeddings at small scale, "no chunking needed" and "no evaluation complexity" claims, illustrative rather than measured numbers, a decision tree that assumes live users, and an LLM judging its own search results. Result: two concrete plan changes, not a rewrite. Full review in the [build log](build-log.md#b-article-review-rag-is-simpler-than-you-think); decision in [0012](decisions/0012-keyword-baseline-and-query-rewriting.md).

*Step 15 follow-up: tested, not just argued.* The article's "start with keyword search" was measured on this project's data: keyword recall 0.66 vs semantic 0.89 for exercises, 0.75 vs 1.00 for passages ([0012 update](decisions/0012-keyword-baseline-and-query-rewriting.md)). Point to make: "The advice fits documentation search, where users type exact terms. My users are coaches describing what they want, and my catalog doesn't reuse their words. I didn't dismiss the advice; I ran it, and the numbers said no for this data."

*Phase 1F F7c follow-up: "cheap query rewriting" tested too.* The article recommended an LLM query rewrite. On this project a plain dictionary matched it on answer quality, fixed one misread the LLM didn't ("BW squat"), and added 0 ms instead of about 640 ms ([0036](decisions/0036-query-rewriting-dictionary-default.md)). Point to make: "The idea was right; the cheapest version of it was enough."

### Why PostgreSQL + pgvector?
Evidence so far:
- [0004. Database: PostgreSQL 16 + pgvector in Docker](decisions/0004-database-postgres-pgvector.md): options compared, tradeoffs, and when to revisit. Now includes a note that the between-Steps-2-and-3 discussion confirmed the rationale.

- [Between Steps 2 and 3](build-log.md#between-steps-2-and-3-understanding-the-database-and-search-types):
  - [SQLite vs PostgreSQL](concepts.md#sqlite-vs-postgresql): a server handles concurrent writes, supports extensions, and matches production. Good story: the developer came from SQLite and Supabase.
  - [pgvector](concepts.md#pgvector): vector column, distance operator, and indexes. Meaning-based ranking and column filters in one SQL query, instead of splitting data across a relational database and a vector database.
  - [Basic vs production-style RAG](concepts.md#basic-vs-production-style-rag): keyword search (built-in full-text search), semantic search (pgvector), and filters (`WHERE`) all run in one database. Only reranking needs an outside model.
  - [Supabase is PostgreSQL](concepts.md#supabase-is-postgresql): Supabase supports pgvector, so the skills and schema transfer to a hosted deployment.
- [Step 3](build-log.md#step-3-docker-compose-start-postgres-confirm-pgvector): now running, not just planned.
  - PostgreSQL 16.15 with pgvector 0.8.6, in Docker via [Docker Compose](concepts.md#docker-compose). Commit `5d66ed2`.
  - [Extension available vs enabled](concepts.md#extension-available-vs-enabled): the image only makes pgvector available; the `ragmotion` database switched it on with `CREATE EXTENSION`. Shown before and after with `pg_available_extensions` and `\dx`.
  - [pgvector](concepts.md#pgvector): the `<=>` cosine distance scale checked by hand (0 identical, 1 unrelated, 2 opposite).
  - [Docker volume](concepts.md#docker-volume): persistence proven. Deleted the container, started a new one, and pgvector was still enabled.
  - [Port mapping](concepts.md#port-mapping) and [0009](decisions/0009-local-db-port-5434-localhost-only.md): checked what other projects used before picking a port, and chose 5434 to avoid a collision. A small story about looking before building.
- [Step 4](build-log.md#step-4-exercise-schema-create-the-table-inspect-it-in-psql): a schema with constraints, tested by trying to break it. Commit `46e9b11`.
  - [Schema](concepts.md#schema) in `db/schema.sql`: 14 columns, one [idempotent](concepts.md#idempotent-script) file that also enables pgvector.
  - [NOT NULL, DEFAULT, UNIQUE, PRIMARY KEY](concepts.md#not-null-default-unique-primary-key) and [CHECK constraints](concepts.md#check-constraints): four bad inserts, four rejections, each naming the rule that failed (`exercise_difficulty_check`, `exercise_equipment_check1`, the not-null on `source`, and pgvector's `expected 1024 dimensions, not 3`).
  - Structured metadata and the `vector(1024)` embedding sit in the same row, which is the payoff of pgvector described above. The vector column also rejects the wrong size, which would catch a mismatched embedding model.
  - [Transaction (BEGIN and ROLLBACK)](concepts.md#transaction-begin-and-rollback): a valid insert was tested and undone, leaving the table empty for seeding.
  - [Identity column and ID gaps](concepts.md#identity-column-and-id-gaps) and [Slug vs id](concepts.md#slug-vs-id): the test row got id 4 because failed inserts used up numbers. A concrete story for why citations use a slug.
  - [0010](decisions/0010-exercise-table-check-constraints.md): why CHECK constraints over free text or lookup tables.
- [Between Steps 4 and 5](build-log.md#between-steps-4-and-5-deployment-options-teach-back-and-a-machine-correction): "Why not Pinecone?"
  - [Dedicated vector database (Pinecone)](concepts.md#dedicated-vector-database-pinecone): Pinecone is vector-only, so it would sit next to Postgres and need syncing on every exercise change. Pinecone does support metadata filters, so the real argument is one source of truth: rows and vectors joinable in one query and updated in one transaction.
  - [Hosted Postgres (Supabase, Neon, etc.)](concepts.md#hosted-postgres-supabase-neon-etc): the same stack is available hosted, so the local choice carries into deployment.
  - Full reasoning in the [0004 note](decisions/0004-database-postgres-pgvector.md#note-2026-09-24-between-steps-4-and-5-deployment-path-and-why-not-pinecone).
- [Step 5](build-log.md#step-5-write-20-exercises-seed-script-query-by-hand): loading data safely. Commit `408130e`.
  - [Upsert](concepts.md#upsert): `INSERT ... ON CONFLICT (slug) DO UPDATE`, only when `IS DISTINCT FROM` shows a real change, reporting inserted vs updated with `RETURNING (xmax = 0)`. Run 1: 20 inserted. Run 2: 0, 0, 20 unchanged. [Idempotent](concepts.md#idempotent-script) by proof.
  - [Transaction](concepts.md#transaction-begin-and-rollback) and [Validate before write](concepts.md#validate-before-write): whole file validated first, all rows written in one transaction, so the table is never half-loaded.
  - Array operators `= ANY` vs `<@` on a `text[]` column, run by hand in psql. See [Array operators: ANY vs contained-by](concepts.md#array-operators-any-vs-contained-by).
  - `db.py` calls `register_vector` so psycopg understands pgvector's type ([0005](decisions/0005-database-access-psycopg-raw-sql.md): hand-written SQL, no ORM).
- [Step 8](build-log.md#step-8-embed-all-exercises-store-vectors-compare-them-by-hand): vectors stored beside the metadata, and the first migration. Commit `6ac4ba8`.
  - All 20 vectors live in the same rows as name, equipment, and difficulty, written with pgvector's `Vector` type in one [transaction](concepts.md#transaction-begin-and-rollback). **Interview-ready summary of the reviewed baseline (Eval walkthrough, 2026-09-28):**
> An LLM drafted my 31-question answer key, and then I reviewed every question myself as a coach, without looking at the system's output. **Interview-ready summary of the baseline (Step 15):**

## Agents

### What makes this an agent rather than a chatbot?
Evidence so far:
- [Phase 2, step 1](build-log.md#phase-2-step-1-the-program-agent-loop-conversation-and-tools): **the program agent.** A chatbot answers each message with text. The program agent has four tools (`find_exercises`, `search_sources`, `ask_user`, `submit_program`) and decides which to call and in what order. Code runs each tool and returns the result; the loop ends when the agent asks the client a question or submits a program that matches a schema. See [Agent (LLM agent)](concepts.md#agent-llm-agent) and [Tool calling](concepts.md#tool-calling-function-calling).
- **Why the existing RAG app wasn't enough.** Asked for a program, it did one search and one answer: 5 exercises with no hinge, three loading schemes listed instead of one chosen, no week layout. The agent's run 2 made 7 exercise searches (one per movement pattern) and 3 dosage searches, then submitted a 3-day full-body program with sets, reps, rest, progression, and cited sources ($0.0012).
- **Guided, not autonomous** ([0045](decisions/0045-program-builder-guided-agent-with-code-guardrails.md)). The developer's words: "not a fully autonomous agent, it's going to be prompted and then use the sources it has." The prompt sets the order of work; filters live inside the tools ([0046](decisions/0046-client-limits-enforced-in-tools-profile-read-by-code.md)); checks will run in code (step 2). See [Workflow vs guided agent vs autonomous agent](concepts.md#workflow-vs-guided-agent-vs-autonomous-agent).
- **The model has no memory.** The message list (prompt, profile, conversation, every tool call and result) is its memory, and the server keeps no state; the client sends the whole conversation each turn. See [The message list is the memory](concepts.md#the-message-list-is-the-memory-stateless-model-stateless-server).
  - Point to make: "It's an agent because the model chooses its own tool calls and can stop to ask the client for missing details. It's a guided one because the prompt sets the order and code decides what the tools are allowed to return."

- [Phase 2, step 2](build-log.md#phase-2-step-2-program-checker-in-code-agent-guardrails-and-the-agent-model-choice): **an agent that has to finish its own job.** When code rejects its program, the agent must fix it and resubmit; it isn't allowed to hand the problem back to the client ([Role confusion](concepts.md#role-confusion-the-agent-hands-its-job-to-the-user)). And it can't start building until it has asked for what's missing ([0052](decisions/0052-agent-building-tools-refuse-until-profile-complete.md)).
  - Point to make: "A chatbot replies. My agent works toward a result that has to pass checks, and code decides both when it may start and when it's done."

- [Phase 2 quality pass, Q1](build-log.md#phase-2-quality-pass-q1-program-quality-checks-the-forced-submit-crash-fix-and-the-q2-and-q3-plan): **an agent's output can be valid and still poor.** A 15/15 program gave chest 3 sets a week and claimed "10–13 sets per muscle group". Code now counts weekly sets and checks quality, and the model is told not to state totals. See [Count, don't trust](concepts.md#count-dont-trust-compute-the-models-claims-in-code).
  - Point to make: "An agent will tell you its work is balanced. Mine said 10 to 13 sets per muscle; chest had 3. Whatever can be counted, my code counts."

## Human-in-the-loop

### Why does a human approve the program?
Evidence so far:

- Point to make: a model can be manipulated, or can guess plausibly ("early 30s" became age 30), and still produce valid-looking output. After: `submit_program` → `ProgramDraft` shape check → `check_program()` → if anything fails, back to the agent with exact fixes and a forced resubmit (up to 3 submissions) → program returned with its checks and `passed_checks`. Empty replies get one nudge, then a clear error. The agent runs on `agent_model` (Gemini 2.5 Flash).

## Tradeoffs

### What would you change if this system had 100,000 users?
Evidence so far:
- [0004](decisions/0004-database-postgres-pgvector.md) revisit signal: millions of vectors or latency beyond what pgvector indexes deliver.
- [pgvector](concepts.md#pgvector): vector indexes (for example HNSW) are skipped for 20 exercises but would be needed at scale.
- [0002](decisions/0002-embeddings-voyage-4-lite.md) revisit signal: embedding cost at scale.
- [0003](decisions/0003-llm-claude-opus-5.md): LLM cost per token and cheaper model options. Superseded in Step 6 by [0013](decisions/0013-llm-openrouter-openai-sdk-qwen.md).
- [0005](decisions/0005-database-access-psycopg-raw-sql.md) revisit signal: add SQLAlchemy and Alembic when the schema changes often.
- [0006](decisions/0006-interface-cli-first.md): no frontend yet.
- [0002](decisions/0002-embeddings-voyage-4-lite.md) tradeoff added in Step 1: the voyageai SDK pulls in LangChain core and LangSmith as [transitive dependencies](concepts.md#transitive-dependencies), which means a bigger install and more packages to keep patched.
- [0010](decisions/0010-exercise-table-check-constraints.md) (Step 4): CHECK constraints with fixed lists vs lookup tables with foreign keys. CHECKs are simple and visible in one file, but adding a new equipment type means editing the schema. Revisit signal: vocabularies grow large or need their own attributes.
- [Schema](concepts.md#schema) (Step 4): schema changes are cheap now, while the table is empty. Once real data and code depend on it, changes go through migrations. [0005](decisions/0005-database-access-psycopg-raw-sql.md) already plans a migration tool (Alembic) for when the schema changes often.
- [Dedicated vector database (Pinecone)](concepts.md#dedicated-vector-database-pinecone) (between Steps 4 and 5): at large scale (tens or hundreds of millions of vectors, very high search traffic) a dedicated vector database becomes a real option, at the cost of running and syncing two systems. At 50 to 5,000 exercises it is not worth it. See the [0004 note](decisions/0004-database-postgres-pgvector.md#note-2026-09-24-between-steps-4-and-5-deployment-path-and-why-not-pinecone).
- [0011](decisions/0011-phase-1-plan-revision-ingestion-and-langsmith.md) (Step 5): plan revision. Catalog first, then RAG, then LangSmith tracing, then ingestion, then evaluation. Tradeoff: ingestion starts about six steps later than "ingestion first", in exchange for failures that can be located. Revisit if the catalog steps drag.
- [Validate before write](concepts.md#validate-before-write) (Step 5): two validation layers (Pydantic and CHECK constraints) give clearer errors plus a safety net, at the cost of keeping two lists of allowed values in sync. See the [0010 note](decisions/0010-exercise-table-check-constraints.md).
- [OpenRouter](concepts.md#openrouter) (Step 5): one key for many models vs an extra middleman and uneven structured-output support. Decided at Step 6 ([0013](decisions/0013-llm-openrouter-openai-sdk-qwen.md)).
- **Cost vs reliability across models** ([Step 6](build-log.md#runs-problems-and-fixes)): same prompt, same two hard tests, total under half a cent.

  | Model | Messy test | Injection test | Cost per call |
  |---|---|---|---|
  | Qwen3 235B | guessed "intermediate", added bodyweight | fell for it | ~$0.0001 |
  | Kimi K2.5 | perfect | resisted | ~$0.003–0.005 |
  | Claude Haiku 4.5 | "beginner" (defensible), otherwise clean | resisted | ~$0.002 |

  Point to make: model choice affects reliability, not just price. Kimi's accuracy came with about 40x Qwen's cost and more latency, from billed hidden reasoning ([Thinking (reasoning) models](concepts.md#thinking-reasoning-models)). The default stayed Qwen (cheapest; the developer's choice), with design defenses covering its weakness. The developer confirmed Qwen as the default after the comparison ([0013 update](decisions/0013-llm-openrouter-openai-sdk-qwen.md#update-2026-09-24-default-confirmed)). At 100,000 users, per-call cost differences of 20 to 50x would matter a lot, so the choice would be made on eval numbers (Step 15).
- [Embedding model lock-in](concepts.md#embedding-model-lock-in) (Step 6): the embedding model is expensive to reverse at scale, because every stored vector must be recomputed on a switch. *Step 7:* guarded in code. The model and its size (1024) sit in `config.py` next to a comment tying them to the `vector(1024)` column, and `embeddings.py` rejects any vector of the wrong size.
- **One provider for both models** ([Step 7](build-log.md#step-7-first-embedding-embed-one-sentence-look-at-the-numbers), [0002 update](decisions/0002-embeddings-voyage-4-lite.md#update-2026-09-24-step-7-confirmed-through-openrouter)): the LLM and embeddings now both go through OpenRouter with one key. Gained: one key, one client, one bill, per-call cost for both. Given up: an OpenRouter outage stops both at once, and Voyage's `input_type` works only because OpenRouter passes it through (verified, not guaranteed). The lock-in that really costs is the embedding model, not the route to it: the fallback is calling Voyage directly with the same model. Point to make at 100,000 users: that single dependency would need a plan (a direct-provider fallback, monitoring).
- [On-the-fly vs pre-computed embeddings](concepts.md#on-the-fly-vs-pre-computed-embeddings) (between Steps 5 and 6): pre-computing trades freshness and easy model switching for fast search. For a small, stable catalog, re-embedding is one script run, so pre-computing wins. At tens of millions of fast-changing documents, embedding at query time becomes worth weighing. See also [Critiquing RAG advice](#critiquing-rag-advice-interview-material).
- [0012](decisions/0012-keyword-baseline-and-query-rewriting.md) (between Steps 5 and 6): keep semantic-first for learning, but prove it against a keyword baseline. Cost: a slightly bigger eval step and one more Phase 1F experiment. Query rewriting, if kept, adds an LLM call per question.
- [0014](decisions/0014-embedded-text-name-description-labels.md) (Step 8): labeled facts in the embedded text help questions about equipment or level match, but pull same-equipment and same-region exercises together (Push-Up next to Inverted Row). Any change to the text means re-embedding everything: one batch call at 20 exercises, a real cost at millions. Revisit with the Step 15 eval.
- **How many results, and whether to cut off by score** ([Step 9](build-log.md#step-9-similarity-search-from-the-command-line-judge-results-by-eye)): a larger k catches more right answers but passes more filler to the LLM; one question had one real match and four fillers. A score cutoff would trim filler, but scores are relative (top scores ranged from 0.725 to 0.533 across good result lists), so the plan is to let the Step 10 LLM judge usefulness and test it in the eval. See [Top-k retrieval](concepts.md#top-k-retrieval). *Step 10: it did. For biceps it used 2 of the 5 retrieved and marked the other 3 "not used"; for "no equipment" it dropped the barbell and band exercises.*
- **Speed vs honesty vs cost across models** ([Step 10](build-log.md#test-runs-and-fixes)), on "what exercises can i do for biceps" (the catalog has no curls):

  | Model | Generation time | Cost per answer | Admitted the missing curls? |
  |---|---|---|---|
  | Gemini 2.5 Flash-Lite | 681–793 ms | $0.000145 | No (said coverage "full") |
  | Qwen3 235B | 4–29 s across runs | $0.000190–0.000325 on this question | Yes (coverage "partial") |

  Point to make: the fast, cheap model was about 20x faster and cheaper in practice, and less honest in this one test. The developer chose Gemini as the default for speed and keeps watching gap honesty; Step 15 decides on eval numbers. At 100,000 users, a 29-second answer isn't viable, and the per-call cost multiplies. See the [0013 update](decisions/0013-llm-openrouter-openai-sdk-qwen.md#update-2026-09-25-step-10-default-switched-to-gemini-25-flash-lite).
- **Prompt rules vs code for constraints** ([Step 10](build-log.md#test-runs-and-fixes)): prompt rules fixed ungrounded advice and a formatting leak, but the equipment mismatch was left for code, because a prompt rule only makes a mistake less likely. See [Hard constraints and negation](concepts.md#hard-constraints-and-negation).

Chosen middle: evidence-only answer plus a labeled general-guidance field. Gained: practical advice (sets, reps, rest). Given up: unverified content now reaches the coach, and code can't judge its accuracy. The first example (60–120 s rest for power work) was doubtful. See [Grounding modes](concepts.md#grounding-modes-strict-vs-labeled-general-knowledge-vs-free-blend).
- **Plan order: documents before tracing** ([0011 update](decisions/0011-phase-1-plan-revision-ingestion-and-langsmith.md#update-2026-09-25-after-step-10-ingestion-moved-before-langsmith), after Step 10): reaching chunking sooner, at the cost of debugging the first chunking bugs without LangSmith traces. *Step 14: tracing added; all Step 11 to 13 bugs had been found from printed stages.*
- **Hosted tracing vs keeping data local** ([0020](decisions/0020-observability-langsmith-wrap-client-decorate-steps.md), [Step 14](build-log.md#step-14-langsmith-tracing-on-the-rag-pipeline)): LangSmith over manual printing only, Langfuse (open source, self-hostable), or plain structured logs. Gained: stored, comparable traces with retriever and LLM views, on a free tier, with little code. Given up: prompts and evidence leave the machine; the code depends on the `langsmith` SDK; free-tier limits (not yet checked). At 100,000 users, trace volume, cost, and personal data in prompts would all push toward sampling, masking, or self-hosting (not decided or tested).
- **UI tool** ([0015](decisions/0015-local-web-ui-fastapi-static-html.md), Step 10): FastAPI + one HTML page over Streamlit or Gradio. Gained a reusable API and keys kept server-side; gave up speed of building (hand-written HTML/JS).
- Scoping story (Step 4): the developer chose to build the simple exercise table first and defer knowledge sources and a document table, rather than design for the full vision up front. See [Before we started](build-log.md#before-we-started-how-much-does-the-table-lock-us-in).
- **Content breadth vs licensing safety** ([0017](decisions/0017-knowledge-source-licensing-policy.md), proposed before Step 11, accepted in Step 11): a tiered license policy uses public-domain and CC BY sources freely and restricted ones only with tags or not at all. Gained: a repo that can be shown publicly and chunks that can be filtered by license. Given up: NSCA's *Essentials*, JSCR articles, and the ACSM 2026 position stand as ingested text; NSCA knowledge now costs the developer's time to write original notes.
- **Layout heuristics vs a general parser** ([0018](decisions/0018-pdf-extraction-pymupdf-layout-cleaning.md), [Step 11](build-log.md#step-11-document-ingestion-extract-clean-page-text-from-the-physical-activity-guidelines-pdf)): cleaning by positions and font sizes measured on this PDF (footer band 50 pt, header band 36 pt, headings 12 pt+, paragraph gap 6 pt, column shift 20 pt). Gained: transparent rules, each a documented constant, with raw text kept for comparison. Given up: the thresholds are document-specific and may need retuning per source; numeric grid tables are untested. Library: PyMuPDF (positions and font sizes, fast) over pypdf (simpler, weaker on layouts) and pdfplumber (better tables, slower); its AGPL license is fine for an open portfolio but needs review for closed commercial use. At scale, with many differently laid-out sources, per-source settings or a general document parser would be worth weighing.
- **Hyphens: keep or delete** (Step 11): keeping line-end hyphens preserves compounds ("moderate-to-vigorous") and leaves a stray hyphen in split words ("cardio-respiratory"). Chosen because a stray hyphen hurts retrieval less than a mangled term.
- **Chunk size and overlap** ([0019](decisions/0019-structure-aware-chunking-150-450-labels-no-overlap.md), [Step 12](build-log.md#step-12-chunking-split-sources-into-passages-and-store-them-in-a-second-table-with-metadata)): chose structure-aware chunks of about 150–450 words with no overlap, over the fixed-size-with-overlap default, section-by-section, and semantic chunking.
  - Evidence: the Guidelines' 256 sections had a median of 116 words, 54 under 50, and 2 over 600. Section-by-section would have made dozens of fragments; fixed windows would cut mid-sentence and blend topics; semantic chunking costs an embedding call per sentence and is harder to debug, usually for a small gain.
  - Size: small chunks lose context, large ones blur the embedding and fill the prompt. Result: median 253 words, 10 of 133 chunks outside the band (3 short at chapter ends, 7 slightly long, max 519).
  - Overlap: dropped in favor of a "title > chapter > sections" label embedded with each chunk. Gained: context without duplicated text. Given up: a passage that leans on the previous paragraph has only the label to help.
  - Also given up: rules tuned to heading-rich documents and dependent on Step 11's heading detection; figures reduce to captions.
  - Revisit: the Step 15 eval against fixed-size, and when research papers or drill manuals are added. Point to make: "The numbers are a first guess based on measurement, and the table stores the chunker version so I can test alternatives instead of guessing twice."
- **Prompt rules vs structural filters** ([Step 13](build-log.md#step-13-test-runs-and-fixes)): population mixing (older-adult numbers given as adult advice) was first tackled with a prompt rule, because it's quick and costs nothing. It helped but didn't hold: one of two retests still slipped. The durable fix is structural: a population tag on each chunk and a retrieval filter, so wrong-group passages never reach the model.
  - Gained by the prompt rule: an immediate improvement with no schema change.
  - Given up: reliability. A rule makes a mistake less likely; a filter makes it impossible for the filtered case. The filter costs a new field, a tagging method (not decided), and the risk of filtering out a passage that was relevant (for example general principles written for all ages).
  - Other levers: a stronger model (more cost), and better retrieval so the right passage ranks first. The Step 15 eval decides which are needed.
  - Same pattern as Step 10's equipment mismatch. See [Prompt rules have a ceiling](concepts.md#prompt-rules-have-a-ceiling-especially-on-small-models) and the [0019 update](decisions/0019-structure-aware-chunking-150-450-labels-no-overlap.md#update-2026-09-25-step-13-population-tags-planned-page-118-skipped).
  - Point to make: "When a mistake matters, I stop asking the model more firmly and change what it's allowed to see."
- **One merged list vs two lists** ([Step 13](build-log.md#step-13-embed-chunks-search-exercises-and-documents-together-answers-cite-both)): exercises and passages are retrieved as two separate top-5 lists rather than one merged ranking (the design as built; a merged ranking was not discussed as an option). Gained: every answer has both kinds of evidence available. Given up: filler on both sides (a dose question still gets five exercises) and more input tokens (about 3,500 per answer). See [One query vector, two tables](concepts.md#one-query-vector-two-tables-combined-search).
- **Keyword vs semantic vs hybrid, measured** ([Step 15](build-log.md#step-15-retrieval-baseline), [0021](decisions/0021-evaluation-design-code-scored-langsmith-semantic-default.md), [0012 update](decisions/0012-keyword-baseline-and-query-rewriting.md)):

  | Mode | Exercise recall | Passage recall | Passage MRR | Forbidden | Verdict |
  |---|---|---|---|---|---|
  | semantic | 0.89 | 1.00 | 0.70 | 0.10 | default |
  | keyword | 0.66 | 0.75 | 0.42 | 0.10 | loses clearly |
  | hybrid (RRF, equal weights) | 0.84 | 0.92 | 0.76 | 0.14 | tune weights first |

  - Keyword search is cheap and exact, but coaches don't use the catalog's words. Hybrid costs a second query and a merge step, ranks the right passage higher, but lost recall with equal weights. At scale, keyword search would need a stored `tsvector` with a GIN index instead of computing it per query.
  - Point to make: "Hybrid is the textbook answer, but my numbers said equal-weight hybrid was slightly worse than semantic alone. I kept semantic and put weighted hybrid on the experiment list, instead of adopting the textbook answer."
  - *F7d update ([0037](decisions/0037-semantic-stays-default-after-hybrid-retest.md)):* weighted hybrid tested with filters. Best weighting 2:1: exercise recall 0.83, passage MRR 0.84, vs semantic 0.87 and 0.86. Hybrid's passage advantage disappeared once the population filter existed. Semantic stays the default.
- **Code evaluators vs LLM judges** ([Step 15](build-log.md#step-15-evaluation-baseline-for-retrieval-and-answers), [Code-based evaluators vs LLM-as-judge](concepts.md#code-based-evaluators-vs-llm-as-judge)): code checks are deterministic, free, and independent of the model being tested. Given up: judging quality of prose or advice, which needs the coach or a judge model validated against the coach's grades. At 100,000 users, sampled human review plus cheap code checks on every answer would be the starting point (not built).
- **Versioned eval datasets** ([LangSmith datasets and experiments](concepts.md#langsmith-datasets-and-experiments)): a new dataset per version of the question file keeps every old result comparable, at the cost of many datasets to clean up later.
- **Top-k vs complete answers** ([Eval walkthrough, part 1](build-log.md#lesson-3-the-reviewed-baseline), [Recall ceiling from top-k](concepts.md#recall-ceiling-from-top-k)): search returns the top 5, which keeps the prompt small, but some questions want everything that fits. After the coach's review, "I only have a pair of dumbbells" expects 7 exercises, so the best possible recall is 5/7 = 0.71; the actual was 3/7, because two forbidden exercises took slots. The key was not trimmed to fit k. The gap stays visible as a finding; what to change (k, filters, or something else) is not decided.
  - Point to make: "A small k keeps the prompt cheap and focused, but my coach-reviewed eval showed it can't hold a complete answer to 'what can I do with only dumbbells'. I kept the honest key and let the eval show the limit."
- **Model choice is still open on eval numbers.** Step 10 said the eval would decide between Gemini (fast, overclaims) and Qwen (slow, more honest). Step 15 ran Gemini only: overclaiming measured at 3 of 29. Running the same experiment with another model is now one setting change; not done yet.
- **Harden first or improve first** ([0023](decisions/0023-phase-1-completion-tests-and-errors-before-retrieval-changes.md), [Step 16 Q&A](build-log.md#step-16-qa-what-the-eval-says-and-what-to-do-next)): with a measured weakness (forbidden checks 2/5) and no tests, the developer chose tests, errors, and the README before the filters. Gained: a safety net before changing core search code, a clean before/after story, faster debugging from clear errors. Given up: the known failures stay a little longer, and eval context has to be picked up again later. Same thinking inside Phase 1F: strengthen the eval before building the filters.
  - Point to make: "I had a clear weakness to fix, but the fix touched core search code with no tests under it. I spent one step on tests first, so when I change retrieval, I'll know in a second whether I broke something, and the eval will tell me whether I improved it."
- **Vocabulary design: `anchor` as equipment** ([0010 update](decisions/0010-exercise-table-check-constraints.md), [F1](build-log.md#phase-1f-begins-f1-exercise-catalog-expanded-to-42)): the Nordic curl uses no weights but needs a partner or an anchoring device. Labeled `bodyweight`, a "no equipment" filter would suggest it to someone who can't do it alone. The coach chose a new value, `anchor`. Gained: filters stay truthful about what a client needs. Given up: one value now covers a person and a device; a client must list `anchor` to see the Nordic curl; one more value to keep in sync in two files. See [Controlled vocabulary](concepts.md#controlled-vocabulary).
  - Point to make: "Designing the equipment list was a coaching decision. 'Bodyweight' would have been technically true and practically wrong for the Nordic curl."
- **Data first vs fix first** ([0024](decisions/0024-phase-1f-order-data-then-eval-then-filters.md)): growing the catalog and rebuilding the eval before the filters delays the fix for the known weakness by two stages, and retires the old 0.91 baseline. Gained: answer keys written once, for the catalog the filters will search, and a before/after comparison that measures only the filters. Also: Claude drafts, the coach reviews, as the authoring method (over writing all 22 by hand or importing from wger), trading some coach time per exercise for speed with an expert check.
- **Word matching vs an AI judge** ([0025](decisions/0025-ai-judge-for-coach-labeling-rules.md), [F2](build-log.md#phase-1f-f2-strengthen-the-eval-and-record-the-before-baseline)): word matching is free and deterministic but rough, and bad at "grouped by muscle group". The AI judge costs about half a cent per judged question (about $0.07 for 13) and can be wrong. Chosen: the judge, but only for the four labeling rules; exact facts stay in code. Judge model Sonnet 5.5 ($2 / $10 per million tokens) over cheaper Gemini flash models, to avoid the answering model's family grading itself. At 100,000 users this would be an offline eval cost, not a per-request cost.
  - Point to make: "I paid for a stronger judge from a different family, because a cheap judge from the same family as the answering model risks sharing its blind spots. It only runs in the eval, not on user requests."
- **Where to enforce "only what I own"** ([0026](decisions/0026-equipment-prefilter-from-llm-read-limits.md), [F3 + F4](build-log.md#phase-1f-f3--f4-read-equipment-limits-from-the-question-and-filter-exercises)): prompt rules (already failing 5 of 13), post-filtering the answer, or pre-filtering in SQL. Chose pre-filtering: forbidden exercises never reach the model, it's deterministic and cheap, and the top 5 fill with usable items. Given up: a misread limit hides good exercises silently, so an over-filtering trap question guards it. Reading the limit with a small LLM call over keyword rules costs one extra call per question (about $0.00003, a few hundred ms) and buys handling of varied phrasing.
  - Point to make: "I chose to change what the model sees instead of asking it to behave. The risk moves from 'suggests a bench exercise' to 'hides a good exercise', which is why I test both directions."
- **Speed vs strict one-step pacing** ([F3 + F4](build-log.md#phase-1f-f3--f4-read-equipment-limits-from-the-question-and-filter-exercises)): reading the limits and the filter were planned as two steps and built as one, at the developer's request. Acceptable because neither does anything alone; the filters themselves still go in one at a time (equipment now, population in F5).
- **How to tag passages by population** ([0027](decisions/0027-population-tags-from-structure-keep-general-filter.md), [F5](build-log.md#phase-1f-f5-population-tags-on-passages-and-a-population-filter)): rules from the document's chapters, an LLM per passage, or by hand. Chose rules: the Guidelines are already organised by population, so tags are free, deterministic, and testable. Given up: every new source needs its own rule, and research papers are tagged general even if a study used one group.
- **What to do with untagged passages** ([0027](decisions/0027-population-tags-from-structure-keep-general-filter.md)): keep only matching tags, or keep general passages too. Chose keep-general, because 132 of 200 passages apply to everyone. Given up: some less specific material still competes for the top 5.
- **Filter passages only, not exercises** ([F5](build-log.md#phase-1f-f5-population-tags-on-passages-and-a-population-filter)): whether an exercise suits an age group is a level or coaching question; no level filter yet, so beginner questions pass only because the retrieved exercises happen to be acceptable.
- **One run vs averaged runs** ([0028](decisions/0028-before-after-averaged-over-three-runs.md), [F6](build-log.md#phase-1f-f6-re-run-the-eval-compare-before-and-after-the-filters-update-the-readme)): single runs are cheap but coverage claims flipped between identical runs. Chose 3 runs per version for the headline comparison (about $0.60 in total). Given up: 3x the cost and time, and 3 runs still can't separate a one-question difference from noise.
  - Point to make: "I paid about 40 cents extra so the number in my README comes from three runs that agree, not one run that might have been lucky."
- **Retry in the judge vs limiting parallel runs** ([0025 update](decisions/0025-ai-judge-for-coach-labeling-rules.md), [F6](build-log.md#phase-1f-f6-re-run-the-eval-compare-before-and-after-the-filters-update-the-readme)): chose wait-and-retry inside `judge_answer()` rather than a global cap on how many evals run at once. Given up: runs that hit the limit get slower, and parallel runs should still be avoided on this account.
- **One k for all questions vs k by question type** ([0029](decisions/0029-exercise-k-stays-5-for-all-questions.md), [F7a](build-log.md#phase-1f-f7a-experiment-with-5-10-and-15-exercises-per-question)): k = 10 everywhere raised completeness (0.80 → 0.92) but lowered answers citing only keyed exercises (87% → 78%), with extras on focused and research questions. The recommended option was adaptive k: 10 only when the intake form reads the question as a list request (`wants_list`). The developer chose k = 5 for every question ("I think we should just do 5"): simpler, and the completeness gain wasn't worth the unasked-for extras. Given up: list questions such as "exercises that need no equipment" stay limited to 5 exercises. The `--k` options stay in the eval scripts for future tests.
  - Point to make: "Cost wasn't the issue; exercise entries are tiny. Noise was. I measured three settings, saw that a bigger k bought 12 points of completeness at the price of messier focused answers, and chose the simple option on purpose. I can rerun the same test if list answers turn out to be too short."
- **Which tool for which failure** ([F7a](build-log.md#phase-1f-f7a-experiment-with-5-10-and-15-exercises-per-question), [Matching the fix to the failure](concepts.md#matching-the-fix-to-the-failure-filters-k-prompt-instructions)): hard limits in filters, breadth in k, presentation in the prompt. F7a showed that a bigger k doesn't fix grouping or labeling. F7b then measured the coach's presentation rules in the answer prompt ([One change at a time](concepts.md#one-change-at-a-time-ablation)): see the next bullet.
- **Presentation rules in the prompt vs the plain prompt** ([0030](decisions/0030-answer-prompt-stays-without-presentation-rules.md), [F7b](build-log.md#phase-1f-f7b-experiment-with-the-coachs-presentation-rules-in-the-answer-prompt-reverted)): three versions (all four rules; grouping only for list questions; labels only) against no rules, 3 runs each. Recommended and pending the developer's confirmation: revert to the plain prompt. Each version padded focused answers or hurt coverage accuracy (111/120 → 104–107/120) and no per-rule gain could be shown on 0 to 4 cases. Given up: the coach's grouping and labeling style isn't enforced yet. Options for later: labels printed by code from the catalog, a stronger answer model, or more exercises for list questions.
